## Why this matters

Most dashboard analytics scan canonical daily `performance_log` rows filtered by date and joined through `ad`. The current indexes support broad organization/ad lookups, but they do not directly target the canonical daily subset used by these hot queries. This plan requires `EXPLAIN` verification first, then adds only indexes that improve the optimized query plans.

## Steps

### Step 1: Capture baseline query plans

Use a local or staging database with representative data. Run `EXPLAIN (ANALYZE, BUFFERS)` for the optimized SQL from Plans 002 and 003. At minimum inspect:

- `adCreative.list` optimized query for `/creatives`.
- `getDailyPortfolioPerformance`.
- `getMerAccountBreakdown`.
- `dashboardStats` portfolio/top/bottom sections if still hot after Plan 004.

Save the important observations in the PR description or a short note in the plan status update. Do not commit raw production data or sensitive values.

**Verify**: each tested query has a captured baseline showing whether time is spent scanning `performance_log`, joining `ad`, sorting, or aggregating.

### Step 2: Choose candidate indexes based on the baseline

Start with the smallest useful set. Likely candidates:

```sql
CREATE INDEX CONCURRENTLY performance_log_ad_date_canonical_idx
ON performance_log (ad_id, date_start)
WHERE
  coalesce(country, '') = ''
  AND coalesce(platform, '') = ''
  AND coalesce(placement, '') = ''
  AND coalesce(device, '') = ''
  AND coalesce(age, '') = ''
  AND coalesce(gender, '') = ''
  AND date_start = date_end;
```

If optimized queries also filter `pl.organization_id = <org>` directly, consider:

```sql
CREATE INDEX CONCURRENTLY performance_log_org_date_ad_canonical_idx
ON performance_log (organization_id, date_start, ad_id)
WHERE <same canonical predicate>;
```

If `EXPLAIN` shows the `ad` side is the bottleneck for account/team filters, consider an `ad` composite index such as `(organization_id, account_id, ad_creative_id)` or `(organization_id, ad_creative_id)`. Add only what the plan proves useful.

**Verify**: for each candidate, explain why an existing index is insufficient.

### Step 3: Express indexes in Drizzle schema or migration

Prefer schema declarations in `src/schema/performance-log.ts` so future snapshots know the index exists. If Drizzle cannot express a partial index cleanly in this version, add a generated migration and annotate the schema limitation in the PR.

If adding partial indexes in schema, you may need:

```ts
import { sql } from "drizzle-orm";
```

Do not hand-edit existing migrations. Add a new migration with `bun run db:generate`.

**Verify**: `bun run db:generate` -> creates exactly one new migration for the index changes.

### Step 4: Re-run `EXPLAIN`

Apply the migration locally or in staging only if instructed by the operator:

```bash
bun run db:migrate
```

Re-run the same `EXPLAIN (ANALYZE, BUFFERS)` queries from Step 1. Confirm the new index is used where expected and total time/buffer reads improve. If an index is unused or regresses the plan, remove it before finishing.

**Verify**: at least one hot query uses each added index, or the index is removed.

### Step 5: Run repo verification

Run:

```bash
bun test
bun run lint
bun run build
```

Expected: all exit 0.
